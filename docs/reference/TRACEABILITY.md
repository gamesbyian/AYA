# Building a measurable coverage inventory

A guide can pass every format check while describing only three of an application's thirty features. AYA therefore uses a separate **inventory denominator**: what was actually discovered in the released app.

## Why two independent artifacts?

- **Product inventory** is generated by inspecting the real app, code, resources, navigational graph, settings definitions, errors, tests, feature flags and support issues, then reviewed. It lists features and tasks that *should* be explained, including negative capabilities.
- **Published reference** contains the factual explanations, recipes and recovery procedures.
- **Gold question set** tests whether a consuming assistant can extract the correct explanations and resist guessing.

Do not generate inventory merely by parsing guide headings. That produces a circular, artificially perfect coverage score.

## Inventory schema (`aya-inventory/v1`)

Create an ordinary UTF-8 JSON file (no YAML dependency):

```json
{
  "schema_version": "aya-inventory/v1",
  "app_id": "dev.example.myapp",
  "app_version": "1.0.0",
  "source_revision": "verified-release-commit",
  "reviewed_at_utc": "2026-10-28T00:00:00Z",
  "items": [
    {
      "id": "TASK-001",
      "kind": "task",
      "title": "Import an item",
      "status": "AVAILABLE",
      "criticality": "high",
      "source_ref": "ui/ImportScreen.kt@verified-commit"
    },
    {
      "id": "F-001",
      "kind": "feature",
      "title": "Cloud sync",
      "status": "PLANNED",
      "criticality": "medium",
      "source_ref": "plans/sync.md@verified-commit"
    },
    {
      "id": "ERR-001",
      "kind": "error",
      "title": "Import failed",
      "status": "AVAILABLE",
      "criticality": "high",
      "source_ref": "ui/ImportError.kt@verified-commit"
    }
  ]
}
```

IDs are permanent identifiers even if UI strings change; do not recycle them. Each item must be supported by a specific source and a clearly recorded version. If a feature has no evidence, label UNKNOWN and give the discrepancy and next verification action in the guide. `PLANNED` entries should be in the limitations section and can also appear as a `F-###` entry.

## Discovery mechanics

Inventory collection is a **two-pass process**:

1. **Mechanical candidate extraction:** identify navigation destinations, route constants, settings schemas, strings, click/gesture handlers, notifications, background services, permissions, storage providers, intents, public APIs, test names, error enums, flags and release-note changes.
2. **Behavioral reconciliation:** inspect released build, exercise core workflows, review screenshots/semantics, determine visibility under flags, and add negative capabilities users frequently assume exist.

An automated extractor can propose IDs and paths but cannot prove behavior. Ask independent reviewers to find omitted screens, hidden states, disabled menus and destructive cases. Inventory the distinction between *code exists* and *feature ships*.

## Coverage calculation

- **Known-item coverage:** discovered entries with an explicitly corresponding guide entry / all discovered entries.
- **Evidence completeness:** guide entries with specific, version-correct source / all guide entries.
- **High-risk coverage:** destructive/auth/security/financial entries with tested preflight, confirmation and recovery / all such discovered entries.
- **Conditional-state coverage:** tested variants / relevant variants identified in the applicability matrix.
- **Question coverage:** held-out support questions answered accurately with the guide / all tested questions.

A perfect known-item coverage score is meaningless if the inventory was shallow. Publish inventory-review evidence, unresolved gaps and an estimate of discovery breadth alongside the score.

## Cross-boundary coverage (optional item annotations)

For an app whose main workflows involve third parties, transactions, notifications, opaque server decisions or irreplaceable content, enrich independent inventory entries with public, non-sensitive annotations. Suggested keys: `authority_actors`, `transaction_state`, `last_reversible_step`, `remote_policy_source`, `remote_policy_verified_at`, `remote_policy_recheck_trigger`, `data_copies`, `failure_layers`, `observable_signals` and `challenge_lenses` (T/A/L/E/R). These are descriptive source-inventory aids, **not** new validator-enforced fields; missing fields cannot be presumed safe. Confirm them by inspecting the released UI, tests and authoritative external sources.

When a high-risk task is within scope, flag missing authority, cutoff, data topology or proof of success as an evidence gap even if every feature ID is represented in the guide. See the [second cross-category stress set](CROSS_CATEGORY_BATCH2.md).

## Automated check

```sh
python3 tools/audit_reference.py \
  docs/reference/EXAMPLE_PARCELPAD.md \
  --inventory docs/reference/examples/parcelpad_inventory.json \
  --questions docs/reference/examples/parcelpad_questions.json
```

The auditor verifies IDs, status labels, evidence, scope consistency, declared inventory coverage and gold-case references. This does **not** prove that the source refs are genuine, guide steps work, or assistant answers are correct. Independent product testing remains mandatory.

## Optional richer tracing

For large apps, attach machine-readable fields such as `screen_id`, `settings_key`, `changed_in_commit`, `prerequisites`, `permission`, `provider`, `release_channel`, `test_id`, `feature_flag`, `safety_impact` and `observed_in_binary`. Keep only public/non-sensitive values. Do not over-constrain small apps to a vast metadata ceremony: the purpose is better coverage and faster maintenance.
