# iOS Files return blocker: evidence-based follow-up research

**Researched:** 2026-11-07 (some GitHub run timestamps are 2026-11-08 UTC). **Scope:** independent, user-selected iOS Files documents into a separate AYA sample host, not output generation or automatic app-to-app IPC. **Status:** research and decision record. No assertion of resolved native picker acceptance.

## Decision in brief

**Most likely failure boundary:** iOS Simulator's LocalStorage File Provider identity/materialization step, *before* the importing host receives a file URL. The evidence is strong for the boundary and moderate, not definitive, for attributing responsibility to Apple's provider. Changing the import parser, size cap or post-selection file coordination cannot fix a system selection that never completes.

**Highest-value next test:** install the independent QA source and Lantern consumer on a **signed physical iPhone/iPad** and repeat one-file plus seven-file, valid plus malformed, through the *same user-driven system Files UI*. Prefer that over yet another speculative fresh-simulator matrix. If physical device succeeds, retain the simulator failure rather than redefining its red tests as green. If it fails, record the OS-selected item's identity and collect sysdiagnose for Apple Feedback Assistant.

**Practical alternate route:** host-registered document Open In merged in [#160](https://github.com/gamesbyian/AYA/pull/160) and its genuine foreign-app-to-host iOS Simulator handoff **passed 2/2 strict native tests** in [merged #162 / run 42431460633](https://github.com/gamesbyian/AYA/actions/runs/42431460633). It supports a tested simulator fallback but does not qualify the still-red native Files picker or arbitrary real assistant apps/physical devices.

## New independent reproduction, 2026-11-08 UTC

[Minimal independent-app native differential 42433068046](https://github.com/gamesbyian/AYA/actions/runs/42433068046) has now answered the next narrower question: **the system picker failure still occurs when the importing app has no AYA code or byte-reader whatsoever.** Two separate erased iPhone Simulators and Xcode 16.4 (16F6) received different numbers of files published by a separate minimal Files app, while both XCUITests selected the same file name and bytes through Apple's actual Files interface.

- **One source file: PASS**; the real picker returned the selected foreign JSON through its completion.
- **Seven source files: FAIL**; a visible, hittable Files item was tapped, but the receiving app remained at `State: picker-opened`, with `Callbacks: 0`. AYA's schema validation, scoped snapshot reader and file coordination do not exist in this isolated consumer.

The [standalone reproduction](../../integrations/apple/file-provider-minimal-repro/README.md), tests and OS log artifacts were merged in [#168](https://github.com/gamesbyian/AYA/pull/168). **Both bounded OS logs were subsequently inspected:** the one-file pass contained **zero** `FP -1005` events; the seven-file failure contained **one**, logged by Apple's `fileproviderd` at `2026-11-08T01:15:56.394Z` for `com.apple.FileProvider.LocalStorage` item `did=6`, approximately **0.756 s after** the XCUITest user tapped the Files cell. This is a highly discriminatory temporal correlation, although the missing `did=6` record is not proven to be that exact tapped file. Exact timestamps and artifact identifiers are frozen in [the structured evidence record](evidence/minimal-files-localstorage-20261108.json). The experiment confirms the same **pre-callback failure boundary** under an AYA-free host; it does not yet prove an Apple implementation defect, the exact provider item ID, or a physical-device failure. Retain the failed native assertion for diagnostic use, and do not repeat the completed simulator matrix automatically. **A signed physical iPhone/iPad comparison remains the next decisive new evidence.**

**Diagnostic interpretation:** Apple's NSFileProviderError.Code.noSuchItem maps to -1005, indicating the referenced provider item cannot be resolved. Apple's NSFileProviderErrorNonExistentItemIdentifierKey identifies the missing item in NSError.userInfo. A visible Files row therefore need not imply a *currently resolvable* backing item. Do not treat the separate DocumentManager "failed opening URL (code 2)" count as diagnostic by itself: the passing swapped-payload lane also emitted that signature.

Reference: [Apple error definition](https://developer.apple.com/documentation/fileprovider/nsfileprovidererror/code); [Apple missing item identifier key](https://developer.apple.com/documentation/fileprovider/nsfileprovidererrornonexistentitemidentifierkey); [Microsoft .NET binding of -1005](https://learn.microsoft.com/en-us/dotnet/api/fileprovider.nsfileprovidererror).

## Platform configuration: no obvious missing entitlement

Apple explicitly says an ordinary app can publish its own Documents into iOS Files without implementing a File Provider extension by configuring **both** UIFileSharingEnabled and LSSupportsOpeningDocumentsInPlace. AYA's independent QA source does set both keys; its own process writes the seven files into its Documents folder, which is exactly the documented local-sharing model. No arbitrary app sandbox enumeration, App Group or custom provider extension is needed or authorized for that scenario.

References: [Apple File Provider overview](https://developer.apple.com/documentation/fileprovider); [Apple UIFileSharingEnabled](https://developer.apple.com/documentation/bundleresources/information-property-list/uifilesharingenabled); [Apple UIDocumentBrowserViewController and local Documents](https://developer.apple.com/documentation/uikit/uidocumentbrowserviewcontroller).

Apple's SwiftUI fileImporter is documented to invoke its completion only after selection or failure, returning a security-scoped URL; simple user cancellation returns without completion. The current red cases are distinguishable because a still-visible selectable document and provider missing-ID OS errors leave the host at picker-opened, *without* an observed cancellation or successful URL.

Reference: [Apple fileImporter completion and cancellation](https://developer.apple.com/documentation/swiftui/view/fileimporter%28ispresented%3Aallowedcontenttypes%3Aoncompletion%3A%29).

## External reports and applicability limits

1. **Specific SwiftUI/UIKit differential (anecdotal, 2025):** a developer reported an iPhone where SwiftUI fileImporter left the sheet open with no callback, but UIKit UIDocumentPickerViewController worked. [Full report and minimal sample](https://stackoverflow.com/questions/79460003/swiftui-fileimporter-not-working-on-a-real-device). It demonstrates a plausible presentation-layer problem *in some configurations*, but AYA already tried UIKit against the broken simulator local provider and obtained no general recovery. This is not a reason to blindly rewrite the importer.
2. **Actual simulator-only picker freezes (independent reports):** [Flutter file picker issue #825](https://github.com/miguelpruivo/flutter_file_picker/issues/825) reported an unresponsive simulator picker that worked on device; simulator reset helped that reporter. [A separate iOS 18 SwiftUI report](https://stackoverflow.com/questions/79441895/swiftui-fileimporter-inside-uihostingcontroller) saw the picker freeze in iOS 18 simulators while one device worked. These concern different projects and symptoms; AYA's many *fresh* simulator tests make "just erase simulator" an especially weak next experiment.
3. **Apple DTS confirms relevant simulator divergence:** an [Apple technical-support response](https://developer.apple.com/forums/thread/713814) warns that the simulator doesn't fully emulate physical iOS sandbox behavior. This justifies signed-device comparison and a refusal to equate simulator failure with universal production failure.
4. **A different known File Provider enumeration bug:** in [Apple's 2025 folder-bookmark discussion](https://developer.apple.com/forums/thread/797469), an Apple DTS engineer cites bug r.150542999 where a first content/enumeration request can return an empty directory and the second works. AYA's symptom is a *visible item* that fails to resolve on selection; do not assume the same bug or add automatic background retries. It raises the value of tracing the exact File Provider item identifier and enumeration timeline.
5. **Modern simulator Files storage behaves differently from app containers:** a [2026 Xcode 27 Device Hub account](https://greatjava.org/2026/10/copying-files-into-xcode-27-device-hub-simulator/) and [Apple forum post](https://developer.apple.com/forums/thread/846994) describe direct simulator Files-storage staging differences. Writing directly into the Files app's internal LocalStorage group could serve as a diagnostic source control, but is an undocumented simulator-only shortcut. It would **not** prove AYA can access another real app's Documents with the user's permission and must never be introduced as production code.
6. **File materialization can fail even with UIKit:** another [2025 developer report](https://stackoverflow.com/questions/79636524/uidocumentpickerdelegate-methoddidpickdocumentsat-not-called-on-a-real-device) captured a system error saying items failed to be prepared/materialized on disk before its delegate callback. The exact root cause and host differ. It supports instrumenting the provider boundary instead of blaming AYA parsing.

## New separate-app Open In observation: representation matters

[Run 42427447880](https://github.com/gamesbyian/AYA/actions/runs/42427447880) recorded the actual native Share Sheet accessibility tree when QA shared its app-owned JSON **file URL**. It contained a genuine selectable cell with identifier "shareCell" and nested "cellTitleLabel" whose label was "AYA Lantern". A subsequent XCUITest mistakenly searched for "AYA Lantern" as that static text's **identifier**, then swiped the source UI, losing the target. The missing test target was an automation bug in that lane, not proof the OS omitted the app.

Later [run 42428250171](https://github.com/gamesbyian/AYA/actions/runs/42428250171), using a custom Transferable FileRepresentation(exportedContentType: json), showed the real activity interface but its visible app row contained only "More", not Lantern. Apple explicitly documents that recipient discovery depends on the Transferable representations advertised. A FileRepresentation is often advisable for file recipients, but the actual AYA simulator evidence for these two representations differed. It would be premature to conclude the generic URL is always better or that FileRepresentation is unsupported.

**Focused evidence-based correction in #162:** return QA to the original source file URL representation that *actually exposed Lantern*; identify the real cell by its nested text's **label**, tap the containing cell rather than any source instructions, avoid swipes that hide available recipients, and require actual destination launch, received bytes, host preview, Cancel/Apply and malformed rejection. Keep the distinct test red until the exact native journey completes. This is a bounded, grounded Open In qualification, **not** another random variant of the #147 picker matrix.

Apple references: [ShareLink and representation-dependent services](https://developer.apple.com/documentation/swiftui/sharelink); [FileRepresentation](https://developer.apple.com/documentation/coretransferable/filerepresentation); [SentTransferredFile copy/open-in-place semantics](https://developer.apple.com/documentation/coretransferable/senttransferredfile/init%28_%3Aallowaccessingoriginalfile%3A%29).

## Priority action and stop decisions

**P0: signed physical-device discriminant.** Use [PHYSICAL_FILES_QA.md](PHYSICAL_FILES_QA.md). Install the signed independent source and importing host without an App Group. Prepare seven synthetic documents *inside the source app*, confirm all seven in Files, and select valid, invalid and over-cap artifacts as a human would. Record device model, iOS build, both app git SHAs, exact filenames, provider identity, observed callback stage, byte-error/semantic-error and screenshots. If the provider refuses selection, capture a sysdiagnose near the failure, scoped File Provider errors and missing item identifiers. Do not upload private data. This is the decisive remaining observation.

**P1: finish independent Open In.** Verify a real OS app target and receiving host, not only plist registration or a Share Sheet preview. If genuine Open In works on device, document it as an optional user-invoked alternative. **The original native picker gate remains red.** If Share Sheet lists a target but no URL arrives, split failure into OS dispatch, document handoff/materialization, and host-owned Inbox/security-scope reading; do not just retry or weaken validation.

**P2: Apple escalation if physical also reproduces.** Apple requests small repro projects and timestamped sysdiagnose/screen recordings through [Feedback Assistant](https://developer.apple.com/feedback-assistant/); File Provider-specific logging instructions/profiles are under [Profiles and Logs](https://developer.apple.com/feedback-assistant/profiles-and-logs/). Include QA host Info.plist, minimal picker host, one-file-pass/seven-file-fail, swapped-content A/B, source-lifetime A/B, actual OS -1005 item identifiers and exact timestamps. AYA's larger repo is poor as an initial Apple reproduction; minimize to two tiny apps. **No Feedback Assistant submission has yet been made.**

**P3: guarded product work while Apple remains unresolved.** Keep the tested manual text-paste return; keep the Open In feature only under its honest capability and acceptance scope; leave import bounded, coordinated, user-selected, semantically validated and separately confirmed. Avoid scanning another app's sandbox, uncontrolled re-enumeration/polling, direct use of simulator LocalStorage paths, caching security-scoped URLs without permission, blanket bypass of security scope checks, or fake fixture injection as a way to make red native tests green.

**Stop rule:** do not add more seven-file simulator permutations. A new test must have a newly observed cause and a specific decision to make. The next externally meaningful work is physical-device evidence or a genuine alternative OS user-mediated handoff.
