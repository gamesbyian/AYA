# CI engineering standard: efficient, trustworthy verification

**Status:** Normative engineering standard for AYA. Read alongside AGENTS.md, current plans, security and module portability contracts. This establishes future requirements, not assertions of current implementation.

## Objective
Maximize trustworthy, immediately actionable defect detection per unit of wall-clock time, runner time, compute, money and agent attention. Every workflow dispatch needs a distinct, risk-relevant evidentiary purpose. No redundant job, suite, build or setup without measured justification. Optimize first actionable failure, safe merge latency, total runner consumption and agent diagnostic time separately. Never weaken coverage, security, provenance or reproducibility for speed.

## Scope and AYA verification map
Audit every workflow, trigger, reusable action, job, condition, matrix, artifact, cache, runner and concurrency group; Gradle/Android/Kotlin tasks; scripts, SDK packaging, host adapters and examples; integration tests; release and documentation validation. AYA's critical boundaries include Android Sharesheet handoff and URI permissions, version-matched reference packets, generic SDK/module interfaces, translation/output imports, optional Filesystem Automation, schema validation and privacy. Enforce docs/MODULE_PORTABILITY.md with independent representative fictional hosts and its existing portability tests. Never couple generic modules or fixtures to other projects or claim a third-party assistant's downstream action was observed.

## Audit and dispatch policy
Inspect live main, open issues/PRs, historical and recent successful/failed/skipped/cancelled runs. Establish baselines for trigger counts, runner minutes, queue/setup/compiler/test times, cache hits, critical path and recurring flakes. Inventory each dispatch's event, exact commit/ref, risk, required evidence, consumers and redundancies. Eliminate duplicate push/PR execution, redundant workflow chaining and unnecessary matrix fan-out. Scope documentation-only changes to lightweight offline checks. Preserve required check names and merge queue/branch protection behavior; a filtered/failed-to-run required check must not become an apparent success. Cancellations must target only superseded equivalent evidence.

## Risk-aware test selection
Use fast static/offline preflight; affected SDK/module compilation and unit tests; cross-module Android and security integration; full release/periodic/high-risk verification. Compute change impact through shared types, Gradle declarations, generated artifacts, schemas and dependencies, not just path prefixes. Ambiguous, multi-subsystem or selector/tooling edits require conservative fallback. Map suites to real defect classes and historical detection yield; remove redundant coverage only with equivalence evidence. Keep real Android intent/permission, packet/import and host-neutral integration checks; mocks cannot attest actual recipient or device behavior. Add deterministic tests for selector rules across docs, Kotlin, build scripts, workflow edits, shared adapters, renames, fork PRs, releases, unknown changes and cancellation.

## Critical path and reuse
Model CI as a dependency DAG. Measure and tune test sharding, job parallelism, Gradle/Kotlin workers, runner CPU/memory/I/O, toolchain setup and artifacts. Reuse immutable verified outputs, safe content-addressed caches, common actions and fixtures where cheaper than rebuilding. Do not assume extra parallelism saves total compute, or that reusable YAML shares outputs. Validate cache invalidation and keep untrusted PR caches/artifacts away from privileged actions and releases.

## Agent-readable diagnostics
Every significant run SHOULD have a concise job summary. Failures MUST, where technically feasible, produce a stable versioned JSON digest plus relevant JUnit/SARIF, with exact SHA/run/job/step, executed vs skipped status, earliest root error, affected module, failed task/test, source line, expected/actual, bounded excerpt, full artifact/log link, reproduction command, classification and next action. Distinguish observed facts from hypotheses; surface setup failures before tests execute. Preserve multiple independent failures and redact secrets and attachment contents.

## Security, reliability and history
Review action pins, token permissions, fork events, injection risks, privacy, release provenance, dependency reproducibility, cache poisoning, secret exposure, flakiness and retries. Preserve first-attempt failure evidence; avoid blanket continue-on-error, hidden quarantines and unbounded reruns. Use historical failures, reverted optimizations and bad test proxies as regression cases.

## Measurement, implementation and exit
Track dispatches, unnecessary fan-out, runner minutes, first actionable failure, safe merge time, critical-path costs, cache effectiveness, test flake rate and digest quality. Compare cold/warm runs across representative changes; do not claim gains from a lucky run. Implement improvements rather than stopping at a plan, safely reconcile overlapping PRs/issues, verify exact heads, update existing authoritative queue/evidence docs and integrate only qualified work. Priority P0 truthful gates/security; P1 eliminate redundant dispatches; P2 critical path/compute; P3 diagnostics; P4 historical defects/flakes; P5 light telemetry. Every workflow must justify its existence. Report baseline, exact changes and links, measured improvement, test evidence, remaining gaps and next steps, distinguishing merged from pending and verified from proposed.
